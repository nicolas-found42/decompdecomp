# Reference helpers for Windows PC games

Research checked on 18 November 2026. Windows projects generated by decompdecomp now expose two read-only tools.
`pe_imports` reports the DLL, name or ordinal, and where the function references the import. `pe_data_refs` reports
relocated data operands with section names and bounded string or hex previews. Function briefs include short
results from enabled tools. The x86 guide explains how to identify a COM interface before naming a vtable call.
The research below explains those choices and records follow-up ideas such as reverse references.

## Start with the information already available

The PC importer already reads import descriptors into an IAT-slot-to-symbol map (`_imports` in
`src/decompnet/consoles/pc/scratch.py`). Named imports lose their DLL association in that map; ordinal imports
become identifier-safe names. `import_thunk` recognizes an x86 `FF 25` jump through an IAT slot, and the same
module supports the x64 RIP-relative form. `_relocations` records external code and data references for delinking.
These are useful foundations: add structured reference evidence without changing the symbols or relocation
rules used by the byte judge. These observations come from the named local functions, not an external format
assumption.

## First helper: imports used by one function

Microsoft's PE specification distinguishes the import lookup table, DLL name, and import address table. PE32
lookup entries are four bytes; the high bit selects ordinal imports, whose ordinal occupies the low 16 bits.
Named entries point to hint/name records. Binding can overwrite IAT entries with addresses, so the lookup table
is the preferred identity source. An RVA is relative to the image base and is not generally a file offset.
[Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

Proposed records should retain `dll`, `name` or `ordinal`, IAT VA/RVA, instruction address, reference kind,
and optional thunk address. Display identity as `DLL!Name` or `DLL!#ordinal`, separately from the identifier
needed to compile. Never present an ordinal's hint or an invented identifier as a recovered export name.

Resolve these bounded instruction forms first:

- `call [absolute-IAT-slot]` and an equivalent tail `jmp`;
- direct relative call or jump to a recognized import thunk, followed by that thunk's jump through the IAT;
- address-taking references to the IAT, identified separately from calls.

Both direct indirection and the linker-thunk form are documented MSVC output: `dllimport` permits an indirect
call, while otherwise the linker can provide a jump thunk. A tool that only searches direct call destinations
will miss one form. [Microsoft: importing function calls](https://learn.microsoft.com/en-us/cpp/build/importing-function-calls-using-declspec-dllimport?view=msvc-170)

Implementation constraints: bound every descriptor, table and string read; reject unmapped/truncated records;
keep DLL identity even when names collide; never load DLLs or execute the target. If the original lookup table
is absent, use IAT contents only when they validate as on-disk lookup entries, and report unavailable identity
otherwise. Register-indirect calls, copied function pointers and wrappers need separate data-flow work; do not
resolve them from a nearby API name. Keep delay imports explicitly unsupported until their separate directory
is parsed: MSVC delay loading uses a helper and load thunk. Runtime `GetProcAddress` accepts either a name or an
ordinal, so ordinary imports are not a complete account of APIs used by a program.
[Microsoft delay-load helper](https://learn.microsoft.com/en-us/cpp/build/reference/calling-conventions-parameters-and-return-type),
[GetProcAddress](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getprocaddress)

Acceptance fixtures should cover a named import, two DLLs exporting the same name, an ordinal, both call forms,
a tail jump, an address-only reference, a non-import indirect call, a truncated table, and a bound-IAT case.
Use synthetic PE fixtures; no DLL downloads or proprietary executable fixtures are necessary.

## Second helper: readable data references

Proposed output should enrich each existing external reference with instruction address, target address,
reference kind, section, and a bounded preview. Preserve address identity even when a preview is available.
For strings, try terminated ASCII and UTF-16LE with explicit encoding and length limits; escape control
characters and mark truncated or unterminated data. Print raw bytes when neither decoding is credible.
These are proposed interpretation rules, not a guarantee that readable bytes are a source-language string.

Start with direct operands and the importer's known relocation targets. Label immediates without relocation
support as candidates. Avoid scanning every numeric constant as a pointer or treating a whole section as one
string. A reverse index can expose other functions referring to the same address. Follow a pointer through
one data cell only as a separate, explicitly indirect reference; pointer arrays, encoded text and computed
addresses remain outside that first version. Keep previews local to project responses and out of repository
fixtures, logs and research notes.

Tests should distinguish code references, strings, string suffix pointers, UTF-16 text, a float or table that
resembles text, unreadable targets, and executable-section immediates. This helper improves evidence available
to an agent; it does not establish the original declaration or automatically justify renaming a symbol.

## Optional guide: COM methods and the x86 ABI

COM interfaces expose ordered method tables and an IID identifies an interface contract. Multiple interfaces
can have distinct interface pointers. Therefore a vtable displacement alone does not identify a method.
[Microsoft interface pointers](https://learn.microsoft.com/en-us/windows/win32/com/interface-pointers-and-interfaces)

An implementable guide can show the interface, zero-based slot, x86 byte offset, method signature, and its
source declaration. Derive the order from actual headers rather than alphabetic documentation lists. Microsoft's
headers provide ordered methods, IIDs, and C macros that pass the interface pointer first:

| Interface | Slot | x86 offset | Method |
| :-- | --: | --: | :-- |
| `IDirect3D9` | 16 | `0x40` | `CreateDevice` |
| `IDirect3DDevice9` | 16 | `0x40` | `Reset` |
| `IDirect3DDevice9` | 17 | `0x44` | `Present` |
| `IDirectInput8A/W` | 3 | `0x0C` | `CreateDevice` |
| `IDirectSound` | 3 | `0x0C` | `CreateSoundBuffer` |

The slots above are counted from Microsoft's declarations, including the three leading IUnknown methods;
offsets are derived as slot times four for x86. This is a reference table conditional on knowing the interface,
not an inference that any call at one of these offsets belongs to it.
[Microsoft d3d9.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/d3d9.h),
[Microsoft dinput.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/dinput.h),
[Microsoft dsound.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/dsound.h)

Document stack cleanup and the explicit interface argument with each signature. MSVC x86 `__stdcall` passes
arguments right to left with callee cleanup; ordinary non-vararg C++ `__thiscall` instead passes `this` in ECX.
Do not draft a COM call using a game's ordinary member-function convention merely because both dispatch through
a table. Verify the exact header's calling-convention macros when producing compilable declarations.
[Microsoft __stdcall](https://learn.microsoft.com/en-us/cpp/cpp/stdcall?view=msvc-170),
[Microsoft __thiscall](https://learn.microsoft.com/en-us/cpp/cpp/thiscall?view=msvc-170)

Keep interface identity evidence separate: a known creation call's return or output parameter, an IID supplied
to QueryInterface, or a verified local declaration can support it. Track pointer copies and overwrites before
propagating that identity. Otherwise display an indirect call and possible interfaces, without assigning a
method name. Pin the exact header revision and record derivation if a generated table ships; these links point
to a moving upstream branch, and modern header syntax need not compile with a historical compiler.

## Recommended order

Ship per-function import evidence first, then bounded data previews and reverse references. Both reuse evidence
already needed by the importer and are testable without running a game. Add the COM guide as a small sourced
reference; automatic interface propagation is a separate project. No recommendation here changes the match
criterion or replaces Ghidra, objdiff, RTTI recovery, or the original compiler.

## Follow-up: obtaining a separate VC6 SP6 toolchain

Microsoft's archived product-updates page confirms that SP6 addressed Visual C++ 6.0 as well as Visual Basic
and SourceSafe. It is an update to those products, not evidence of a standalone compiler entitlement.
[Microsoft product updates](https://learn.microsoft.com/en-us/previous-versions/aa700916(v=msdn.10))
The historical English full-package entry was
`https://www.microsoft.com/en-us/download/details.aspx?id=9183`; its historical binary URL was
`https://download.microsoft.com/download/1/9/f/19fe4660-5792-4683-99e0-8d48c22eed74/Vs6sp6.exe`.
The entry returned 404 during this check, as did a HEAD-only request to the binary URL. No proprietary package
was downloaded. Thus a presently working official public download has **not** been established. Microsoft's
currently accessible Visual Basic SP6 security rollup updates controls, not the VC6 compiler.
[Microsoft VB6 security rollup](https://www.microsoft.com/en-us/download/details.aspx?id=50722)

The official Microsoft-hosted archived SP6 overview says MDAC, the Microsoft VM and Internet Explorer updates
are excluded, and that installing SP6 removes an existing Visual C++ Processor Pack. Preserve a Processor Pack
installation separately; do not assume that SP6 plus that pack is a supported combination. The overview is
Japanese; the statements here paraphrase the indexed text.
[Microsoft SP6 overview](https://download.microsoft.com/download/4/9/1/4915E136-7EE3-4D8A-9529-B988266649E6/vstudio_downloads_sp_VS6SP6.pdf)
Exact English-package prerequisites, a requirement for SP5 first, installer compatibility with current systems,
and rights to extract/overlay this particular package remain unverified from an available primary installer
readme/EULA. They must be checked against the user's authentic media before proceeding. Do not substitute a
VB-only service pack or a runtime redistributable. Visual Studio 6.0 is out of support.
[Microsoft servicing status](https://learn.microsoft.com/en-us/visualstudio/releases/2022/servicing-vs2022)

The concrete next route is an already-owned, licensed VC98 installation or authentic service-pack media,
not republishing a compiler pack. First locate the user's copy and inspect its readme/EULA and file versions.
If that copy's terms permit the intended use, prepare a separate installation/copy and retain the original;
apply the matching service pack through its documented installer in an isolated compatible Windows environment.
A raw file overlay is only a technical experiment until its manifest, prerequisites and license are checked:
the update may include libraries and headers as well as the backend. No blanket permission to duplicate,
redistribute, or bypass installer checks was established by this research. No installation or overlay was tried.

For verification, inspect **`VC98/bin/c2.dll`**, not just the `cl.exe` banner. The local
`src/decompnet/kits/visualcpp.py` already prefers `c2.dll`'s PE file-version resource, then `c2.exe`, then
`cl.exe`, and accepts owned `VC98` folders. This is an existing implementation observation; it is not proof
that a particular local copy is SP6. Record full file versions and SHA-256 hashes for the driver, backend,
frontends and linker, then compile a tiny synthetic C/C++ fixture with that separate toolchain. Verify which
files were loaded and inspect the resulting object and linked image before selecting it for a project.
Compare the backend build with compilation records, not a linker-version field or a product label; mixed
records do not establish that every function was compiled by one backend. A build number such as 9782 is a
selection lead until checked against the actual owned backend. This research did not independently establish
the SP6-to-9782 mapping from Microsoft's file manifest. The existing guide's statement about `cl.exe` build
8804 must not be treated as a backend-version claim.

A limited filename inventory in conventional local tool/cache locations found no independently verified
SP6 compiler or service-pack package. This is not a whole-disk search or proof that the user owns no such copy.
